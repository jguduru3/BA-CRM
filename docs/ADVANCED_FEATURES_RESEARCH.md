# Advanced feature research

How the "advanced features" were chosen: a multi-source research run (parallel
web searches, primary vendor documentation fetched, every claim put through a
3-vote adversarial check) on what leading B2B CRMs ship that this CRM lacked.
Implemented from it: weighted forecast + forecast categories, stage history /
funnel / win-loss / velocity analytics, deal-health score with risk flags,
duplicate detection + merge, round-robin routing, multi-channel sequences with
response-aware exit logic, and Idempotency-Key support on the API.

Question: What advanced, high-value features do leading modern B2B sales CRMs (Salesforce Sales Cloud, HubSpot Sales Hub, Pipedrive, Zoho CRM, Attio, Close, Folk) offer in 2025-2026 that a mid-size internal CRM (Spring Boot 3 / Java 21 backend, React 18 frontend, PostgreSQL; already has leads, opportunities pipeline/kanban, companies/contacts, tasks, activity timeline, role-based permissions with team scopes, audit log, WhatsApp + email integration, AI scoring/summaries via Claude/OpenAI, campaigns, custom Notion-style databases, whiteboards, CSV export, an integration Master API with API keys and HMAC-signed webhooks) should add next? Focus on: (1) sales forecasting and pipeline analytics (weighted forecast, deal velocity, stage conversion, win/loss analysis, forecast categories), (2) lead/deal health scoring and AI-assisted next-best-action and deal risk signals, (3) duplicate detection/merge and data enrichment, (4) workflow automation and sequences (multi-step email/WhatsApp cadences, SLA timers, round-robin lead assignment / territory routing), (5) integration/API best practices (idempotency keys, cursor pagination, webhook delivery guarantees, OpenAPI), and security/compliance expectations (GDPR data export/erasure, field-level audit, SSO/SCIM). For each feature, give what it is, why it matters (evidence of business value), how leading CRMs implement it, and a concrete implementation approach suited to this stack, ranked by value-to-effort.

## Summary

The 25 verified claims point to five feature areas for the BA-CRM stack, listed here by value-to-effort. (1) Forecasting: add a weighted forecast (amount x stage probability, the HubSpot default) with forecast categories mapped per pipeline stage and ordered (Not forecasted < Pipeline < Best case < Commit < Closed won). Add funnel and win/loss conversion reports. Like Pipedrive, count a won deal as having passed every stage and a lost deal as stopping at its last stage. This is low effort with existing opportunity/stage data plus a stage-history table, and high value. (2) Duplicate management: separate matching rules (exact plus fuzzy matching, e.g. Jaro-Winkler and phonetic) from duplicate rules (warn, block, or allow and report, on create and on edit). Add a merge where the primary record's values win, its empty fields are filled from the secondary, activities and associations move over, the oldest created date is kept, and merged IDs are recorded. Vendors treat merges as irreversible. (3) Multi-channel sequences (email/WhatsApp) need three behaviours: pause on any inbound reply, skip steps for which the contact lacks data instead of refusing enrollment, and after an unrecoverable failure (bounce, undeliverable) skip later steps on that channel only. (4) Deal health: a 0-100 composite score built from CRM signals (stage velocity, time in stage vs. historical norms, close-date slips, stakeholder coverage) and activity signals (recency and frequency of contact, sentiment). Show it next to the rep-entered probability, and send automatic risk flags to the owner and manager. (5) API hardening: Stripe-style idempotency keys on POST/PATCH (client-generated, up to 255 characters, response stored once execution starts, parameter-mismatch error, kept at least 24h) using the IETF Idempotency-Key header. The verified evidence did not cover cursor pagination, webhook delivery guarantees, OpenAPI, GDPR export/erasure, field-level audit, SSO/SCIM, round-robin routing, SLA timers or enrichment. Recommendations in those areas rest on general engineering practice, not on these sources.

## Findings (ranked by value-to-effort)

### Weighted forecast plus forecast categories (rank 1, high value / low effort)

Weighted forecast plus forecast categories (rank 1, high value / low effort). HubSpot's default forecast amount is Amount x Deal probability, with Total amount as an alternative. Each pipeline's stages map to ordered forecast categories (Not forecasted, Pipeline, Best case, Commit, Closed won). A category's meaning comes from its position in that order, not its label, and an optional automation keeps the category in sync when a deal changes stage. Implementation for this stack: add probability and forecast_category columns to the pipeline-stage config (category as an ordinal enum). Snapshot the weighted amount on opportunity save, and add a forecast endpoint grouped by owner/team scope, period and category, with rep overrides stored separately.

Confidence: high (verification vote 3-0). Sources: https://knowledge.hubspot.com/forecast/set-up-the-forecast-tool

Evidence notes: Claims [0] and [1] were both verified 3-0 against HubSpot's current primary documentation. The defaults' labels can be edited, so the five category names are mapping options, not a fixed set.

### Stage conversion and win/loss analytics (rank 2, high value / low-medium effort)

Stage conversion and win/loss analytics (rank 2, high value / low-medium effort). Pipedrive offers a funnel conversion report: one column per stage showing the % of deals that reached it, with the overall win rate on top. It also offers a win/loss report with deal owners as the default columns. In the funnel, a won deal counts as having completed every stage wherever it actually closed, and a lost deal counts as stopping at the stage where it was lost. Open deals are excluded by default. Implementation: add an append-only opportunity_stage_history table (opportunity_id, from_stage, to_stage, entered_at, user), filled by the existing service layer or audit hook. Compute conversion and time in stage (deal velocity) with SQL window functions, apply the won-counts-all-stages rule, and render charts in React.

Confidence: high (verification vote 3-0). Sources: https://support.pipedrive.com/en/article/insights-reports-deal-conversion

Evidence notes: Claims [2] and [3] were verified 3-0 against Pipedrive's primary help article. The attribution rule applies to the Insights conversion report specifically.

### Duplicate detection with separate matching rules and duplicate rules (rank 3, high value / medium effort)

Duplicate detection with separate matching rules and duplicate rules (rank 3, high value / medium effort). In Salesforce, matching rules find candidate duplicates and duplicate rules decide the action. The admin chooses block or warn (allow, with optional alert and report), set separately for create and for edit. Reps can bypass warnings, and the duplicates they create show up in reports. The standard contact/lead rule uses fuzzy matching: First Name uses Exact, Initials, Jaro-Winkler, Metaphone 3 and Name Variant, and Title uses Acronym, Exact and Kullback-Leibler distance, so 'VP' matches 'Vice President'. Zoho's de-duplicate tool matches on at most 3 user-chosen fields, e.g. Email + Company. Implementation: use PostgreSQL pg_trgm/fuzzystrmatch (similarity, levenshtein, dmetaphone) with normalized email, phone and domain columns and indexes. Add a DuplicateRule entity (object type, fields plus algorithm, threshold, action on create and on edit). The create/update APIs return potential duplicates with a 409 or a warning payload, and bypasses are logged to the audit log.

Confidence: high (verification vote 3-0). Sources: https://trailhead.salesforce.com/en/modules/sales_admin_duplicate_management/units/sales_admin_duplicate_management_unit_2, https://help.zoho.com/portal/en/kb/crm-v2-1/manage-crm-data/duplication-management/articles/crm-v2-merge-duplicate-record

Evidence notes: Claims [15], [16], [17] and [13] were verified 3-0 against primary vendor documentation from two vendors. The algorithm list applies to Salesforce's standard Contact/Lead rule, not its Account rule.

### Record merge semantics (rank 4, high value / medium effort)

Record merge semantics (rank 4, high value / medium effort). HubSpot: the surviving record combines activities, associations and most properties. The primary record's value wins a conflict, and the secondary's value is used only where the primary is empty. Exceptions: the furthest lifecycle stage and the oldest create date are kept, and the secondary's email/domain is added as a secondary value. The merged record gets a new ID, a 'Merged [object] IDs' property keeps the history, and merges cannot be undone. Zoho: at most 3 records per merge with one master. Attachments, notes and activities move to the master, created time and created-by come from the oldest record, stage history is not carried over, and the duplicates are deleted permanently. Implementation: a transactional MergeService that re-points foreign keys (activities, tasks, timeline, associations, campaign memberships, WhatsApp/email threads) to the master. Apply primary-wins and fill-empty rules per field, with a side-by-side picker in the UI. Store merged_ids[] and a full JSON snapshot of the losing records in the audit log (this enables a manual restore, which the vendors do not offer). Emit a record.merged webhook.

Confidence: high (verification vote 3-0). Sources: https://knowledge.hubspot.com/records/merge-records, https://help.zoho.com/portal/en/kb/crm-v2-1/manage-crm-data/duplication-management/articles/crm-v2-merge-duplicate-record

Evidence notes: Claims [10], [11], [12] and [14] were verified 3-0. Both vendors document irreversible merges, and Zoho's 3-record limit is confirmed by its API v8 docs.

### Multi-channel sequences with response-aware exit logic (rank 5, high value / medium-high effort)

Multi-channel sequences with response-aware exit logic (rank 5, high value / medium-high effort). In Close, an inbound email or SMS, an answered call, or a call the rep marks as responded pauses the sequence and marks the contact responded by default (configurable through the workflow goal; auto-replies don't count). Contacts missing data a step needs are still enrolled, and those steps are skipped. After an unrecoverable failure (bounce, failed call, undeliverable SMS), the sequence continues but skips later steps of that same channel. Implementation: Sequence and SequenceStep entities (channel, delay, template) and an Enrollment entity (state, current step, next_run_at, skipped_channels). A ShedLock-guarded scheduler, which the repo already has, runs due steps. The inbound WhatsApp/email webhook handlers set the enrollment to RESPONDED, and bounce/undeliverable callbacks add the channel to skipped_channels.

Confidence: medium (verification vote 3-0). Sources: https://close.com/changelog/sequence-improvements

Evidence notes: Claims [18], [19] and [20] were verified 3-0, but all come from a single vendor's 2023 changelog. Close's current help center confirms the pause behaviour, while the same-channel skip-after-failure rule has no 2025-26 confirmation (medium on [20]).

### Deal health score, AI win probability and risk flags (rank 6, high value / medium effort with a rules-first approach)

Deal health score, AI win probability and risk flags (rank 6, high value / medium effort with a rules-first approach). Revenue.io's Opportunity Health Score is a 0-100 composite. CRM inputs: stage progression/velocity, forecast-category movement, deal size, close-date pull-ins and slips, time in stage vs. historical benchmarks, stakeholder coverage. Activity inputs: sentiment trend, engagement breadth, recency and frequency of contact across channels. A separate AI predictor's close likelihood is comparable to the rep's stage probability, which exposes gaps between rep optimism and the evidence. Risk flags (sentiment decline, champion disengagement, stalled stage or slipping close date, missing economic buyer, unaddressed competitor) go automatically to the owner and manager. Gong's score is a percentile rank against other open deals, not a probability, from a model trained on each customer's own outcomes using 300+ signals. Implementation: a nightly job computes deterministic features from stage history, close-date change history (audit log), activity timestamps and contact roles. Combine them into a weighted 0-100 score (later fitted with logistic regression on won/lost history), with the score shown as a percentile until calibrated. The existing Claude/OpenAI integration extracts sentiment, competitor mentions and economic buyer presence from emails and WhatsApp messages and produces a next-best-action. Risk-flag rules create tasks and notifications for the owner and manager.

Confidence: medium (verification vote 3-0). Sources: https://support.revenue.io/revenue-intelligence/getting-started-with-revenue-intelligence/revenue-health-score-model/, https://help.gong.io/docs/understanding-ai-deal-predictor.md

Evidence notes: Claims [4]-[9] were verified 3-0 against primary docs, but both vendors are revenue-intelligence add-ons rather than the CRMs named in the question, and no source gives evidence of predictive accuracy or business value.

### Idempotency keys for the Master API (rank 7, high value / low effort)

Idempotency keys for the Master API (rank 7, high value / low effort). Stripe v1 stores the status and body of the first request with a key once execution begins and replays it on retries, including 500 errors. Requests that fail validation, or conflict with one still running, are not stored. Keys are client-generated (V4 UUID or similarly high-entropy, up to 255 characters, no sensitive data), can be pruned after at least 24h, are treated as new once pruned, and a retry with different parameters is an error. The IETF draft defines an Idempotency-Key header (a structured-header String, at most one per request) to make POST/PATCH fault-tolerant. Implementation: a Spring OncePerRequestFilter or HandlerInterceptor on the Master API. An idempotency_keys table keyed by (api_key_id, key) stores the request hash, status (IN_PROGRESS/COMPLETED), response code, body and created_at, and is inserted with ON CONFLICT. Return 409 while in progress and 422 on a hash mismatch, replay completed responses, and purge rows after 24h-7d with a ShedLock job.

Confidence: high (verification vote 3-0). Sources: https://docs.stripe.com/api/idempotent_requests, https://www.greenbytes.de/tech/webdav/draft-ietf-httpapi-idempotency-key-header-01.html

Evidence notes: Claims [21]-[24] were verified 3-0. Stripe docs are primary and current, scoped to API v1 (v2 differs). The IETF document is an Internet-Draft, not an RFC.

## Caveats
Several areas in the research question had no verified claims: cursor pagination, webhook delivery guarantees (retries, ordering, replay), OpenAPI, GDPR export/erasure, field-level audit, SSO/SCIM, round-robin/territory routing, SLA timers, data enrichment, and quantified business-value evidence (ROI or win-rate lift) for any feature. Rankings in those areas, and the value-to-effort ordering overall, are engineering judgement, not sourced findings. All sources are vendor documentation, which shows what products do, not how much they help. Deal-health evidence comes from add-ons (Revenue.io, Gong), not from the named CRMs (Attio, Folk and Close's AI features were not covered). The Close sequence claims rest on a 2023 changelog, only partly re-confirmed by current docs. Stripe's idempotency rules are specific to v1, and the IETF header is still a draft. The implementation sketches assume the repo's existing ShedLock, audit log and webhook infrastructure; I did not check them against the codebase.
